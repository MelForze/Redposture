# Эскалация сетевого таймаута по попыткам (вариант A)

Дата: 2026-09-02
Статус: фаза 1 реализована (тесты зелёные: 3363 passed)

## Статус реализации (фаза 1)

Сделано: фундамент `transport.escalating_timeout` + `classify_failure_reason`
+ предикаты; эскалация в обоих HTTP-слоях (`http_session`, `http_api`) с
отказом ретраить `refused/dns/network/tls` и сохранением ретрая stale
keep-alive (`CannotSendRequest/RemoteDisconnected/ResponseNotReady` по
`isinstance`); дефолты `--timeout` 1.0→3.0 и proxmox 3.0→5.0; точный
классификатор в ClickHouse (первый retry-блок), чтобы серверный
`max_execution_time` не считался сетевым; тест-гарантия отключения
лесенки в elastic mass-profile.

Отложено в следующую фазу (см. соответствующие разделы): вся
TCP-connect эскалация (`zookeeper`/`oracle`/`mongodb`/`docker`/`kafka`),
поле записи `attempt_timeouts`, отдельная ветка `partial-read`.

## Проблема

Все модули используют единый `--timeout` (дефолт 1.0 c) и `--retries`
(дефолт 3), объявленные в `redposture_core/cli_args.py`. Переопределяют
таймаут только два модуля: `proxmox` (3.0) и `zookeeper`/`keeper` (5.0).

Retry-цикл (`redposture_core/clients/http_session.py:322-337` и TCP-клиенты)
повторяет попытку фиксированным таймаутом и **не различает причину
падения**: `connection refused` и `connection timeout` ретраятся
одинаково, хотя ведут себя противоположно:

- `connection refused` — порт закрыт, хост жив — приходит **мгновенно**.
  Рост таймаута на такой хост влияния не оказывает; повтор бесполезен.
- `connection timeout` — порт задроплен фаерволом (silent drop) — это
  единственный случай, где мы реально ждём весь таймаут.

Из-за этого фиксированный низкий таймаут теряет **живые, но медленные**
хосты (ответ приходит позже 1 c), а фиксированный высокий — раздувает
хвост скана на **задроплённых** портах.

Худший случай сейчас на DROP-порт: `1+1+1+1` c + backoff
`0.2+0.4+0.8` ≈ **5.4 c** на цель.

## Цель

Первая попытка остаётся дешёвой; живым-но-медленным хостам даётся второй
и третий шанс с растущим таймаутом. Платить за рост только там, где он
осмыслен — на `timeout`-хостах, а не на `refused`.

## Границы

- Трогаем: TCP connect-таймаут в клиентах и HTTP retry-цикл
  (`HttpSession`).
- **Не трогаем** серверные бюджеты, привязанные к тому же параметру:
  ClickHouse `send_receive_timeout`
  (`modules/clickhouse/actions.py:489-491`), MongoDB
  `serverSelectionTimeoutMS` (`clients/mongodb.py:182`), ZooKeeper
  `session_timeout_ms` (`clients/zookeeper.py:893`). Эскалация «таймаута»
  на этих слоях меняет поведение сервера (длина сессии, лимит выполнения
  запроса), а не наше сетевое ожидание. Они остаются на базовом
  таймауте.

## Решения (зафиксированы с заказчиком)

1. **Базовый таймаут поднимается минимум до 3 c везде.** Глобальный
   дефолт `--timeout` меняется с 1.0 на **3.0**.
2. **Абсолютная лесенка ступеней, без множителей.** Таймаут попытки
   задаётся формулой:

   ```
   ladder(base) = [base, max(5.0, base), max(7.0, base)]
   ```

   где `base` — эффективный базовый таймаут (per-module дефолт либо явный
   `--timeout`). Ступени 5 и 7 — абсолютные полы; если база выше — берётся
   база. Примеры:

   - `base = 3` (глобальный дефолт) → `3 → 5 → 7`
   - `base = 5` (zookeeper/keeper/proxmox) → `5 → 5 → 7`
   - `--timeout 8` → `8 → 8 → 8`

3. **Per-module override сохраняются как пол лесенки:**
   - `proxmox` поднимается `3.0 → 5.0`.
   - `zookeeper` / `keeper` остаются `5.0`.
   - Остальные модули наследуют глобальный дефолт `3.0`.
4. **Явный `--timeout` = первая ступень.** Пользовательское значение
   задаёт `base`; лесенка достраивает ступени по формуле выше. Явно
   заданный `--timeout` уважается даже ниже 3 c (быстрый скан — право
   оператора); флор 3 c — это про дефолт, не про жёсткое ограничение
   ввода.
5. **`connection refused` — окончательная причина, не ретраится.** Порт
   закрыт → одна попытка → сразу `fail`.

Число ступеней лесенки согласуется с `--retries` (см. «Число попыток»).

## Причина падения: классификация

### Текущее состояние (корректно для отображения)

Централизованный нормализатор `utils.friendly_error_text`
(`utils.py:95-141`) раскладывает сырое сообщение по непересекающимся
веткам в приоритете: tls → refused → timeout → dns →
network-unreachable → operation-not-permitted → errno-фолбэк. Ветки
через `if … return`, поэтому одна запись = одна причина; склейки
«connection refused timeout» в коде нет. Клиенты `zookeeper`, `grpc`,
`kafka` — обёртки над `utils`; `oracle`, `mongodb`, `docker` — свой
маппер с той же семантикой (в `oracle.py:123-126` порядок timeout→refused
обратный, но в одной строке обе подстроки не встречаются).

Вывод: на **отображение** причины можно полагаться.

### Проблема для решений

Классификатор `transport.is_connection_timeout`
(`clients/transport.py:35-38`) матчит подстроку `"timeout"`. Он ловит и
**прикладные** таймауты, не сетевые: ClickHouse `max_execution_time`
(`modules/clickhouse/discover/engine.py:138`), gRPC `DEADLINE_EXCEEDED`,
Kafka-коды `INVALID_SESSION_TIMEOUT`/`INVALID_TRANSACTION_TIMEOUT`.

Разведка (~25 вызовов): большинство — `_is_connection_timeout_fail_record`
поверх `record["error"]`, который к моменту вызова **уже нормализован**
(строго `"connection timeout"`) — для них substring-match безопасен.
Риск сосредоточен в точках, где на вход идёт **сырой** текст исключения
в модуле с прикладным «timeout» — показательный `ClickHouse
_is_timeout_error(text)` (`modules/clickhouse/actions.py:371`) в
retry-маркерах. Таких мест единицы.

### Изменение

- Добавить в `transport.py` **точный** классификатор причины по
  нормализованному префиксу (`startswith("connection timeout")`,
  `startswith("connection refused")`). Существующий
  `is_connection_timeout` оставить для обратной совместимости.
- Decision-точки эскалации/ретрая перевести на точный классификатор.
- В точках, где на вход идёт сырой текст (ClickHouse retry-маркеры),
  прогонять его через `friendly_error_text` **до** классификации.

## Реализация

### Слой 1 — HTTP retry-цикл (`HttpSession`)

`clients/http_session.py:322-337`. Сейчас: `attempts = retries + 1`,
таймаут фиксирован, `_transient_error` ретраит всё транзиентное.

Меняем:

- Классифицировать `request_error` точным классификатором.
- `refused` / `dns` / `network-unreachable` → **не** ретраить (окончательно).
- `timeout` / `reset` → ретраить, повышая таймаут по лесенке: попытка
  `n` использует `escalating_timeout(base, n)`. (`partial-read` отдельной
  веткой не выделен — см. «Стоимость и край».)
- stale keep-alive (`CannotSendRequest`/`RemoteDisconnected`/
  `ResponseNotReady`) → ретраить (переоткрытие соединения), опознаётся по
  `isinstance` независимо от текста ошибки.
- `SSLCertVerificationError` → `tls` → не ретраится (сохранено).

### Слой 2 — TCP connect в клиентах — ОТЛОЖЕНО (следующая фаза)

`clients/oracle.py`, `clients/zookeeper.py`, `clients/kafka.py`,
`clients/mongodb.py`, `clients/docker_engine.py`,
`utils.filter_open_tcp_hosts_for_credential_file`. Общий хелпер
эскалации connect-таймаута для этих клиентов **не реализован в этой
фазе** — у них нет единого attempt-цикла, куда встроить эскалацию, и это
существенная работа. Перенесено в следующую фазу целиком.

Важно: попытка тронуть только диагностическое поле ZooKeeper
`znode_count_attempt_timeouts` (без реальной эскалации в ZK connect) была
сделана и **откачена** — запись лесенки, которую connect не применяет,
давала оператору ложную диагностику. ZK-эскалация вернётся вместе с этим
слоем.

### Дефолты таймаута по модулям (после изменения)

| Слой | base | Лесенка попыток |
|---|---|---|
| Глобальный дефолт (`cli_args.py`) | 3.0 | 3 → 5 → 7 |
| proxmox | 5.0 | 5 → 5 → 7 |
| zookeeper / keeper | 5.0 | 5 → 5 → 7 |
| явный `--timeout N` | N | N → max(5,N) → max(7,N) |

### Число попыток

**(Уточнено при реализации.)** Число попыток = `retries + 1`
(историческое поведение, не меняется). Лесенка задаёт таймаут КАЖДОЙ
попытки: `escalating_timeout(base, i)` = base, max(5,base), max(7,base),
а для `i ≥ 3` держит `max(7,base)`. При дефолтном `retries=3` это 4
попытки с таймаутами `[3,5,7,7]`. Прежняя формулировка про
`min(retries+1, len(ladder))` **отменена** как противоречащая клампу
лесенки (кламп для `i≥3` осмыслен только если попыток может быть >3) и
как ломающая семантику `--retries`. При `retries=0` (elastic) — ровно
одна попытка (лесенка не разворачивается, используется только `base`).

### След попыток в записи — ОТЛОЖЕНО (следующая фаза)

Поле `attempt_timeouts` (список применённых таймаутов) для HTTP-слоёв
**не реализовано в этой фазе** — базовая ценность (эскалация + отказ
ретраить refused) от него не зависит. Обобщение паттерна на
`HttpResponse`/`AuditRecord` перенесено в следующую фазу вместе со
Слоем 2.

### Elastic mass-profile

`modules/elastic/stage.py:110-127`. При `endpoint_count >= 10_000`
профиль принудительно жмёт таймаут (сейчас к 1.0). Лесенка в этом режиме
**отключается** (одна попытка, без эскалации) — точность здесь
сознательно принесена в жертву throughput. Базовое значение mass-profile
пересматривается вместе с новым дефолтом (см. открытые вопросы).

## Стоимость и край

- Худший случай на DROP-порт при дефолте (`retries=3` → 4 попытки):
  `3+5+7+7` c + backoff ≈ **~22 c** против нынешних 5.4 c. Смягчается
  тем, что `refused` (основная масса «мёртвых» в типичном скане) больше
  **не** ретраится вовсе и падает за одну мгновенную попытку.
- Рост base поднимает первую ступень и, через клампы, всю лесенку.
- `partial-read` (`http.client.IncompleteRead` с чистым EOF) в этой фазе
  **не** ретраится отдельной веткой (классифицируется как `other`) — это
  совпадает с прежним поведением `_transient_error`; RST-усечения
  по-прежнему ретраятся через ветку `reset`.

## Тестирование

Unit:

- Точный классификатор: нормализованный вход → верная причина; сырой
  прикладной ClickHouse-timeout (`max_execution_time`) → **не** считается
  сетевым timeout.
- `ladder(base)`: `3 → [3,5,7]`, `5 → [5,5,7]`, `8 → [8,8,8]`,
  `1 → [1,5,7]`.
- HTTP retry: `refused` не ретраится (одна попытка); `timeout` идёт по
  лесенке; `attempt_timeouts` заполняется; `reset` эскалирует;
  `SSLCertVerificationError` не ретраится.
- TCP connect-хелпер: та же матрица причин.
- Op-бюджеты (ClickHouse `send_receive_timeout`, Mongo
  `serverSelectionTimeoutMS`, ZK `session_timeout_ms`) **не** подхватывают
  лесенку — остаются на базовом таймауте.
- Elastic mass-profile (≥10 000): лесенка отключена, одна попытка.
- `--retries N` корректно ограничивает число ступеней.
- Дефолты модулей: proxmox=5.0, zk/keeper=5.0, глобальный=3.0 (проверить
  через `--help` / парсер).
